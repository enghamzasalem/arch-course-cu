### Part 3: Replication and Optional Event Log

**Task 3.1: Data Redundancy**

**1. Postgres Synchronous versus Asynchronous Replication**
In the CityBite architecture, the PostgreSQL database infrastructure employs distinct replication strategies to balance data integrity and system performance. Synchronous replication is strictly utilized for the primary failover replica. This configuration guarantees strong consistency, ensuring that every write operation is securely recorded on both the primary node and the backup node before the client receives a successful acknowledgement. Consequently, the Recovery Point Objective is practically zero, as no committed transactions are lost in the event of a catastrophic failure of the primary database. In contrast, asynchronous replication is deployed for the read replicas that serve the analytical reporting and internal dispatch operations. This mechanism optimizes write performance on the primary node by allowing the secondary databases to synchronize in the background. While this introduces a non-zero Recovery Point Objective and eventual consistency for the dispatch views, it strategically prevents heavy reporting queries from degrading the core transactional throughput.

**2. Misconfigurations and Split-Brain Scenarios**
A critical risk in replicated database architectures is the occurrence of a split-brain scenario or persistent stale reads due to misconfigured automated failover mechanisms. If a network partition occurs and the failover system incorrectly assesses the operational primary node as offline, it may prematurely promote a backup replica to an active primary status. This results in a catastrophic split-brain state where two disconnected databases independently process and commit conflicting customer orders. Reconciling these divergent data histories requires complex manual intervention and invariably leads to data loss, duplicated kitchen efforts, or financial discrepancies. Furthermore, if routing mechanisms mistakenly direct transactional validations to an asynchronous replica that is lagging behind the primary, the application may process stale reads, causing customers to view outdated order statuses or successfully purchase inventory that has already been depleted.

**3. The CAP Theorem and Read Path Availability**
The CAP theorem dictates that a distributed stateful system cannot simultaneously provide strong consistency and continuous availability when subjected to a network partition. For the CityBite platform, the architectural design deliberately favors availability over strong consistency for specific non-transactional read paths, such as the estimated time of arrival display and general menu browsing. During a network partition or a severe synchronization delay, the system is engineered to serve eventual consistent data from local caches or asynchronous read replicas rather than completely rejecting the user request. This operational prioritization ensures that mobile clients experience a highly responsive and functional interface, accepting the minor business trade-off that a delivery estimate or geographical tracking coordinate might temporarily reflect a slightly obsolete state.
